## When to use an API key

DaySurface has two ways to authenticate, and **OAuth is the default**:

- **OAuth sign-in (interactive clients).** Claude, ChatGPT and other MCP
  clients sign the user in through DaySurface's OAuth 2.1 server and receive
  short-lived session tokens: a 1-hour access token and a single-use refresh
  token that rotates on every refresh. Signing out revokes them all. Use this
  whenever a person is present to sign in.
- **API keys (non-interactive clients only).** Scripts, CI jobs,
  server-to-server integrations and MCP clients that can only send a fixed
  header cannot open a browser to complete an OAuth sign-in. API keys exist
  for those cases only.

Because an API key is a long-lived secret rather than a session token, it is
constrained:

- Only a signed-in user can create one, and its scopes cannot exceed the
  creator's.
- Give it the narrowest scope template that works, and set `expires_in_days`.
- DaySurface stores only a SHA-256 hash of the key; the full key is shown once,
  at creation.
- An expired or revoked key is refused immediately. Revoke a key the moment it
  is no longer needed (see [Revoke a key](#revoke-a-key)).

## API Key Authentication

Include your API key in the `X-API-KEY` header:

```bash
curl -H "X-API-KEY: sk_..." \
  https://api.daysurface.com/api/v1/auth/me
```

```json
{
  "user_id": "user_01abc",
  "email": "user@example.com",
  "auth_method": "api_key"
}
```

Enterprise SSO via WorkOS is also supported.

## Managing API Keys

### Create a key

```bash
curl -X POST https://api.daysurface.com/api/v1/auth/api-keys \
  -H "X-API-KEY: sk_..." \
  -H "Content-Type: application/json" \
  -d '{"name": "my-integration", "scope_template": "standard", "expires_in_days": 90}'
```

Use a scope template for common permission sets:

| Template | What it allows |
|----------|---------------|
| `read_only` | Read config and billing info |
| `standard` | Read + execute tools + manage billing |
| `admin` | Everything |

Or provide explicit scopes:

```json
{ "name": "limited-key", "scopes": ["services:read", "services:execute"] }
```

### List your keys

The endpoint is cursor-paginated. Pass `limit` (1-100, default 20) and follow
`next_cursor` until `has_more` is `false`:

```bash
curl -H "X-API-KEY: sk_..." \
  "https://api.daysurface.com/api/v1/auth/api-keys?limit=20"
```

```json
{
  "items": [
    { "id": 42, "key_prefix": "sk_ab12cd34", "name": "my-integration", "revoked": false }
  ],
  "next_cursor": "eyJjIjoiMjAyNS0wMS0xNVQxMDozMDowMCswMDowMCIsImkiOjQyfQ",
  "has_more": true
}
```

Fetch the next page by passing the cursor back verbatim (treat it as opaque):

```bash
curl -H "X-API-KEY: sk_..." \
  "https://api.daysurface.com/api/v1/auth/api-keys?cursor=eyJjIjoiMjAyNS0wMS0xNVQxMDozMDowMCswMDowMCIsImkiOjQyfQ"
```

Cursor pagination (rather than `offset`/`page`) avoids duplicate rows under
concurrent writes and offset drift. It does not provide a point-in-time
snapshot, so keys created after the walk starts can still be missed by a later
page fetch. Pass the same `limit` value on each request until `has_more` is
`false`.

### Revoke a key

```bash
curl -X DELETE -H "X-API-KEY: sk_..." \
  https://api.daysurface.com/api/v1/auth/api-keys/{key_id}
```

## Scopes

Each API key has scopes that control what it can do:

| Scope | Description |
|-------|-------------|
| `services:read` | Read tool metadata |
| `services:execute` | Call tool endpoints |
| `billing:read` | View usage and subscription info |
| `billing:write` | Report usage |
| `admin:read` | Read admin data |
| `admin:write` | Admin operations |

<Callout type="info">
No HTTP endpoint currently requires `admin:read` or `admin:write`. Administrative
functions (`config`, `doctor`) are **CLI-only** - they have no REST route, so
they cannot be reached over the network regardless of scope. Use the `daysurface`
CLI (`daysurface config …`, `daysurface doctor`) for those operations. The
`admin:*` scopes remain defined so existing keys that carry them stay valid.
</Callout>

Wildcards: `*` grants all scopes, `services:*` grants all service scopes.

A new key's scopes cannot exceed the creating key's scopes (no privilege escalation).
